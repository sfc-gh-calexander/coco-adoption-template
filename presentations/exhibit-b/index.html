Vertical Patterns

Four production patterns from real-world CoCo deployments. All anonymized. Each includes what was built, the data involved, the outcome achieved, and which HoL phase it maps to. The patterns span both agents and applications - CoCo is not limited to one build type. Use these to frame the conversation before the build, not as scripts.

Pick the tab closest to your customer's industry, or work through all four for the full pattern library.

Restaurant and Hospitality

Executive Reporting Agent and Corporate Chatbot

An AI agent that lets non-technical executives and operations managers ask questions about their restaurant data in plain English. Answers in 10 seconds, generated SQL visible and auditable.

The data

POS transaction data, labor scheduling, food cost tracking, and marketing spend - all in Snowflake, all connected through a single semantic view.

Discovery questions that surfaced this

  • "What does your CFO spend most of their time pulling manually?" - weekly sales-by-location report
  • "Where does that data live?" - Snowflake, several tables joined in a view
  • "What would they ask it if they could just type?" - "What were our top 5 markets last quarter by margin?"

Outcome

The first session produced one deployed agent answering margin and revenue questions. That single session catalyzed 12 additional AI workstreams across the organization - finance, operations, marketing, and culinary - built by the customer's own teams without additional SE involvement.

Semantic view structure

3 tables (transactions, locations, menu), 6 dimensions (location, date, category, region, channel, menu_item), 4 metrics (gross_sales, net_sales, food_cost_pct, labor_pct). 2 verified queries.

HoL mapping: Phase 2 (semantic view) is the most important phase for this vertical. Get the business names right - "net sales" not "NET_SALES_AMT" - and add verified queries for the CFO's top 3 questions.
Financial Services ISV

Embedded Geospatial Analytics Agent

A natural language interface for geospatial data, embedded into the ISV's own product. Their customers type plain-English questions like "Which ZIP codes in Austin have the highest risk exposure?" and get answers powered by Snowflake and the ISV's spatial datasets.

The data

The ISV's proprietary geospatial datasets, already in Snowflake Marketplace. The build connected their semantic view to a CoCo agent, then embedded the agent in the ISV's product via the Cortex Agent API.

Discovery questions that surfaced this

  • "How do your customers interact with your data today?" - they write SQL or use a BI tool
  • "What do they wish they could ask?" - natural language queries against spatial attributes
  • "What's the one spatial question every new customer asks?" - risk density by geography

Outcome

Every customer of the ISV now gets natural-language access to spatial data as part of the ISV's own product. The pattern scales to the ISV's entire customer base without each customer building anything independently.

Semantic view structure

2 tables (coverage_zones, risk_factors), 8 spatial dimensions (zip_code, county, state, flood_zone, risk_tier, property_type, coverage_type, region), 3 metrics (avg_risk_score, total_coverage, exposed_value). 5 verified queries for the most common spatial patterns.

HoL mapping: Phase 3 (agent) is where the differentiation lives for this pattern. The tool description needs to specify what spatial dimensions are available and when to use them vs. when to say it cannot answer.
Healthcare Platform

Governed Clinical Query Agent

An AI agent for a healthcare data platform that lets non-technical clinical staff query operational and research data without writing SQL. Governance controls are applied at the semantic view layer, not the application layer.

The data

De-identified clinical event data, patient cohort definitions, and operational metrics. PHI-adjacent columns masked via Snowflake column masking policies before being exposed in the semantic view.

Discovery questions that surfaced this

  • "Who in your organization needs data but cannot write SQL?" - clinical operations team, research coordinators
  • "What stops them from getting it today?" - they have to request it from the data team, 3-5 day SLA
  • "What would they ask if they could get it instantly?" - "How many patients in cohort X completed the protocol?"

Outcome

A reusable deployment pattern for regulated healthcare accounts. The governance setup is documented and reproducible. New healthcare accounts deploy the same pattern in one session using this template.

Semantic view structure

3 tables (patients, events, cohorts), dimensions using business names that match clinical vocabulary, masking policies on date-of-birth and geographic identifiers, verified queries for the 5 most common protocol compliance questions.

HoL mapping: Governance setup (column masking, RBAC) happens before Phase 2. Document the data steward's approval of the exposed columns before the session. Phase 2 takes 45 minutes instead of 30 for regulated data.
Note: A dedicated data governance skill (providing pre-built patterns for BAA-scoped deployments) will be added to Phase 3 of the HoL when available. For now, apply masking policies to the source tables before creating the semantic view.
SaaS and Internal Tools

Internal Application Factory

8 internal production applications in a single-day hackathon by the customer's own engineering team. Applications included a customer churn predictor, an inventory status dashboard, a support ticket classifier, a pricing model tester, and four vertical-specific operational tools.

The data

The customer's existing Snowflake tables - operational data, CRM data, and support logs already in Snowflake.

Discovery questions that surfaced this

  • "What internal tools do your engineers build requests for that never get prioritized?" - 6-8 tools on the backlog
  • "Where is the data for those tools?" - all in Snowflake
  • "What if your engineers could ship those tools without a sprint?" - that's the session design

Outcome

Self-sufficient adoption. The customer's engineering team builds new CoCo applications independently, without SE engagement. The pattern was replicated at a second account the following month by sharing the session runbook.

Session structure (different from the standard HoL)

This pattern works as a group hackathon. One SE, multiple engineers, 4-hour session. SE demonstrates one build end-to-end (45 min), engineers split into pairs and build independently (2.5 hours), closing review and deployment (45 min).

HoL mapping: Skip the AE-focused setup. Run Phase 1 (discovery) as a group brainstorm. Each pair runs Phases 2-4 in parallel. Phase 5 (handoff) is replaced by a group retrospective and a shared repo of what was built.

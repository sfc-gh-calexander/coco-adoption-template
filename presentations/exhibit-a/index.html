CoCo Capabilities Reference

What CoCo can and cannot do, the product boundaries, and common misunderstandings that come up in every session.

What CoCo is

CoCo is an AI coding agent embedded in Snowflake. It has access to your Snowflake environment, can read schema and data, write and execute SQL, build Snowflake objects, and create applications. It runs inside your Snowflake governance boundary.

Start with Capabilities and work through the tabs in order. When you are done here, head to Vertical Patterns.

Section 1 of 3

Core Capabilities

Six things CoCo builds and analyzes directly against your Snowflake data.

Build

AI Agents

Create Cortex Agents that answer questions using Cortex Analyst (text-to-SQL), Cortex Search, or custom tools. Wired to semantic views for accuracy.

Build

Applications

Build Streamlit apps, Snowflake Apps, and internal dashboards directly against Snowflake data. No separate infrastructure.

Build

Data Pipelines

Author dbt models, Dynamic Tables, and stored procedures. CoCo reads your schema and writes correct SQL for your specific data.

Analyze

Schema and Data

Read table schemas, sample data, and relationship metadata to inform what it builds. Always working from your actual data, not assumptions.

Analyze

SQL Debugging

Explain and fix failing SQL, diagnose query performance, and suggest schema improvements based on usage patterns.

Assist

Documentation

Generate column descriptions, table comments, and semantic view annotations automatically from data samples and column names.

What CoCo does not do

  • It does not answer questions from the internet or general knowledge - only from your Snowflake data
  • It does not ingest external data on its own - data must already be in Snowflake or loaded via standard pipelines
  • It does not autonomously modify production objects without confirmation - it proposes changes, you execute them
  • It does not persist conversation history across sessions by default
Note: CoCo can build many kinds of things against your Snowflake data - agents, apps, dashboards, pipelines, notebooks. When the target is a text-to-SQL agent specifically, a semantic view still provides the data model that grounds its accuracy; that is one build pattern, not CoCo's core job.
Section 2 of 3

Common Misunderstandings

The objections and misconceptions that come up in nearly every first session.

"This is the same as ChatGPT"

ChatGPT answers from training data and the internet. CoCo answers from your Snowflake tables. The data never leaves your environment. Every answer is SQL against your schema.

"It needs a lot of data prep first"

CoCo can work with raw tables. The semantic view layer provides the business context. You do not need a fully modeled data warehouse before the first demo.

"The answers aren't reliable"

Accuracy is a function of the semantic view quality. Add verified queries for common questions and the model uses them reliably. Accuracy is measurable and improvable.

"We need our data team to build this"

A semantic view is a SQL CREATE statement. An agent spec is DDL. Your data team can version-control, review, and deploy these like any other database object.

Section 3 of 3

Governance

CoCo inherits Snowflake's existing access model - there is no separate permission system to reason about.

CoCo inherits Snowflake's RBAC model. The agent accesses only what the executing role can access. You control what data the semantic view exposes. For regulated data (PHI, PII, financial), apply column masking policies to the underlying tables before exposing them in a semantic view.

Audit: all queries generated by Cortex Analyst are logged in SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY with a QUERY_TAG identifying the agent.
